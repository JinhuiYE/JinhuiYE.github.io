ABSTRACT

Frontier models such as GPT-6-Astra have shown that they can control robots, and many groups now use simulated benchmarks to explore how far they can go. But unless the evaluation setup rules it out, a score on an embodied benchmark can blend what the model can do, what the harness around it does, and what an agent could learn from simulator state within its reach. We put each benchmark behind a wall: it runs as a separate service, the agent sees camera images and robot state and sends actions, and nothing else crosses. Behind that wall we ran one constrained test across 14 benchmarks: the GPT-6-Astra Native Policy, with no benchmark-specific harness, no simulator access and one prompt for all. The aim is not a high or low score but a clear baseline that any other method can be measured against on the same services.

1Benchmarks as services

In most evaluation setups, the policy and the simulator run side by side, often in the same process. That is convenient, but it puts the agent right next to everything that defines the task: the scene layout, where the objects are, how success is scored. We pull the two apart. Each benchmark runs as its own service, on its own machine, and the agent sits on the other side of a wall.

The only things that cross are camera images and robot state going out, and actions coming back. Each turn, the agent sends one to five actions. The service checks them, runs them in the simulator and returns the next set of images. That is the whole interface.

✓The agent receives
  • The task instruction
  • Camera RGB images
  • Robot state (joints, end-effector pose)
  • The action space: dimensions, units, frames
  • Which of its actions were executed
✕The agent never receives
  • Ground-truth object poses or contacts
  • The scene layout or reset seed
  • Reward, success, or how scoring works
  • Simulator files and other episodes
  • Any built-in skill or fallback policy

Running benchmarks as services gives us two things. The first is isolation: the agent can reach the task only through what it sees and the actions it sends, never through the simulator itself. The second is breadth: any benchmark that speaks this small interface becomes one more service, so the same agent can be run on many of them in exactly the same way. Because the interface only carries what a real robot could sense and do, the same wall can later stand in front of physical hardware too. The next two sections explain why each of these matters.

2Why isolation matters

Early on, before we had the wall, we watched an agent do something sensible and troubling. Before its first move, it opened the simulator's layout file, counted the objects in the scene and noted roughly where each one was. Then it planned. Nothing in its instructions said not to. It was simply using what was within reach.

That is the problem with running the simulator next to the agent. The scene configuration, the assets, even the scoring code sit in the same workspace as the agent. An agent that reads them may still finish the task, but the score no longer says much about whether it can see and act. This is not a flaw of one model or one paper. Any capable agent will take the shortcuts its setup allows, ours included. So rather than asking agents to look away, we think evaluations should take the shortcut off the table: keep the simulator on the other side of a wall, so that a score can only come from what the agent sees and does. That is what starBenchServer is built for.

3Why breadth matters

Isolation keeps the simulator out of reach. It does not stop an agent from fitting one test. A single benchmark covers one slice of robotics, with its own robots, scenes and tasks, and an agent can be tuned until it does well on that slice. A high score there says little about the next benchmark.

Our answer is breadth. We put as many benchmarks as we can behind the same wall and run them all the same way: tabletop and bimanual manipulation, kitchens and households, humanoids, indoor navigation, long-horizon and safety tasks, perturbed scenes and moving targets. Tuning for one suite does not help on the other thirteen, so gains that come from knowing a particular test show up as unevenness across the set instead of hiding in a single number. Each new benchmark is just one more service, so the list is meant to grow.

4The GPT-6-Astra Native Policy

Robot agents are increasingly built to improve themselves. In a recursive self-improvement (RSI) loop, the agent studies its failures, rewrites its own prompts, tools and skills, and tries again, often with a person in the loop who decides which failures matter and which fixes to keep. Pointed at one benchmark, such a loop can bring in knowledge of that benchmark itself: the people steering it learn its scenes, its tasks and where its scorer is strict, and that knowledge ends up in the agent. Scores rise, but they no longer show plainly what the model can do on its own.

So before improving anything, we wanted the starting point. What does GPT-6-Astra do when nothing has been tailored to the task in front of it? The Native Policy is our attempt to measure that: one model, one short prompt and one setup, carried unchanged across all 14 benchmarks.

At a glance
The model seesthe task instruction, camera RGB and robot state. Nothing else.
The model outputsthe benchmark's own numeric actions, one to five at a time, chosen by the model.
No specific harnessone generic setup for every benchmark, never tuned to its failure modes; no demonstrations and no task-specific prompts.
Whyit is the baseline: what a general model does before anything is built for a particular benchmark.
Prompt excerpt (verbatim) 
You are the autonomous direct-control policy for one robot episode. Choose
native numeric actions from the supplied task instruction, current public RGB,
declared robot state and acknowledged execution. There is no fallback policy,
task-solving service, learned action proposal or hypothetical simulator.

Inspect action_spec and state_names before choosing actions. Their dimensions,
units, frame, rotation and gripper conventions belong to the selected service.
Do not assume a robot, number of arms, camera names, frequency, coordinate offset
or action meaning from a familiar benchmark. Missing state remains unknown.

For continued control, call robot_act with the current request_id, actions as
an ordered list of native vectors, a concise public reason, and stop_reason=null.
Each row requests one control. Choose between 1 and max_chunk_length rows;
repetitions and replan timing are your choices within that ceiling.

Compare the next RGB and declared robot state with the effect you expected.
Revise ineffective actions using public evidence; no scripted recovery is run.

Use only the actor-owned workspace and supplied public evidence. Do not connect
to a simulator, request resets or hidden observations, inspect object truth,
scores, layouts/seeds, native assets, evaluator files or other episodes.

The model keeps one running conversation per episode and looks at fresh images before each move. The same short prompt is used for all 14 benchmarks and never changes during a run. It cannot declare success either: each benchmark's own evaluator decides, at the benchmark's own time limit.

5Evaluation on 14 Benchmarks

Blue bars are the Native Policy. Gray bars show, for comparison, the best published result on the same benchmark from a frontier model, whether it acts through a harness or outputs actions directly. We leave out systems with a learned robot policy (a VLA or world-action model) in the loop.

Most blue bars sit below the gray ones, sometimes far below. On LIBERO the best published result is 99.9% and the Native Policy entry shows 50%; on MetaWorld it is 96% against 71.2%, on CALVIN 99.6% against 82%, and on LIBERO-Plus, where every scene is perturbed, 92.4% against 43%. On RoboCasa Tabletop the two are close, 19% against 12.5%. The Native Policy struggles most on long tasks that need careful contact: bimanual sorting in RoboDojo, household chores in BEHAVIOR and humanoid tabletop work.

Published setups also differ from ours in ways that tend to raise scores: task subsets, demonstrations, longer step budgets or task-specific prompts. So we read the gap as a measurement, not a verdict. It shows, benchmark by benchmark, how much those choices can add on top of the Native Policy today.

Navigation is the exception. On VLN-CE, across the 11 unseen scenes, the Native Policy reached the goal on 314 of 373 routes (84.2%, SPL 0.72). The best published result we found from a frontier model without a learned navigation policy is 83.0% (SPL 0.71), on a 100-episode subset of the same split. Both runs cover only part of the 1,839 episodes, so the two are roughly level rather than one ahead.

7Evaluate your agent

If you have an agent, with or without a harness, you can run it behind the same wall. Your agent decides how it plans, which models it uses and what it remembers; the benchmark decides what happens when an action runs. You do not need a copy of the simulator.

  1. Start a benchmark service. Install the benchmark's simulator and assets following its setup guide, then launch its server with a fixed configuration, seed and output directory. 
    rsi-bench list
rsi-bench serve --benchmark simpler_env \
  --parameters /abs/benchmark-parameters.json \
  --seed 7 --episodes 1 --port 8765 \
  --output-dir /abs/new-run/server
  2. Connect your driver. Call describe to get the benchmark's observation and action format, open an episode and reset it once, then send actions with step and read the reply after each one until the episode ends. The repository includes a single-case driver template you can copy.
  3. Give your agent only what the protocol allows. The model sees the observations and sends robot actions; server credentials stay in your driver.
  4. Read the results. Every closed episode produces a result record with outcome, counters and errors. Interaction history and videos are recorded by default and can be turned off. 
    python -B -m benchkit.reports.basic_result \
  --run-dir /abs/closed-run/client \
  --output-dir /abs/report/my-run

Results are reported per benchmark and per method. An agent with a harness, extra models or a tuned prompt shows up as its own entry, next to the Native Policy baseline.

What we take away

One constrained setting, many benchmarks. Running every benchmark behind the same wall, with the same generic setup, gives a baseline that is comparable across 14 suites rather than tuned to any one of them.

A general model already does a lot. With nothing tuned to the benchmark and the simulator out of reach, GPT-6-Astra completes a good share of tasks. Most numbers sit below published harness results, which is what the constraints should produce.

The gap is useful. It measures, benchmark by benchmark, how much the machinery around a model adds beyond the model itself.

Comparable numbers are still scarce. Published results use different subsets, budgets and aids, and two of the 14 benchmarks, VLA-Arena and DOMINO, have none at all. With the wall in place, like-for-like numbers are straightforward to produce, for this model and the next.

Limitations

Can the agent really not reach the simulator? We cannot rule it out completely. What the wall does is close the most direct paths, so the risk is much lower. The simulator, its assets and the scoring code run on a different host. Nothing from the benchmark side reaches the agent except images, robot state and replies to its actions, and the only way the agent can affect the world is by sending actions.

Some paths lie outside the wall. An agent's own setup can look things up on the open web, including a benchmark's public source code, and a user can hand it extra information. The benchmark side cannot prevent this. These are choices of the method, so they should be declared with its scores. In our runs, the agent had no network access, and its workspace held only its own notes and the observations it received.
